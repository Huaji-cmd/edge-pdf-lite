# M8 · 高亮必须"染背景"，不能"盖色板"

> 用户反馈原话：**"你实现的高亮是在字之上蒙了一层不太透明的板然后在板上面加颜色，
> 我希望的是高亮能直接在字下面的背景加颜色，不会影响字本来的颜色。你的高亮已经影响到字本来的颜色了。"**
>
> 结论：**根因是 alpha 不满格，不是混合模式选错了。** 两条渲染路径都要改成
> `Multiply + alpha = 1`。app 内端到端 **62/62** 通过（`npm run test:interact`），
> 四套回归合计 **145 项全绿**。

---

## 一、根因：Multiply 只对了一半，alpha 才是那一半

`M6` 已经给高亮的 `/AP` 加了 `ExtGState /BM /Multiply`，当时验的是"文字不再被实心色块盖住"。
但**只看"盖不盖住"不够** —— 用户看到的是"字被染色了"，这是另一件事：

| 做法 | 白底 | 黑字 (0,0,0) | 观感 |
|---|---|---|---|
| 普通填充（不透明） | 黄 | **黄** | 字完全消失 |
| 半透明填充 α=.55 | 0.45·白 + 0.55·黄 | 0.45·黑 + 0.55·黄 = **(14,101,77)** | 字被冲成灰绿 ← **用户看到的** |
| Multiply，α=.55 | 插值 | 介于黑与乘积之间 → 仍偏灰 | 还是被冲淡 |
| **Multiply，α=1** | 1·黄 = **黄** | 0·黄 = **(0,0,0)** | ✅ 只有背景上色，字一个像素都不动 |

Multiply 的数学恰好就是"只染背景"：`0 × 任何色 = 0`，黑字乘什么都是黑。
但**前提是 α=1** —— α<1 时浏览器/查看器会在"原色"和"乘积"之间插值，
黑字会被拉向高亮色，看起来就是"蒙了层半透明的板"。

两处都要改，缺一不可：

| 位置 | 错误写法 | 正确写法 |
|---|---|---|
| 写回 PDF 的 `/AP` | `{ BM:'Multiply', ca: a.opacity, CA: a.opacity }` | `ca: 1, CA: 1` |
| 注释字典的 `/CA` | `CA: a.opacity` | 高亮固定 `1`（这是查看器在 `/AP` **之上**再叠一次的 alpha） |
| app 内渲染 | `ctx.globalAlpha = a.opacity` | 高亮强制 `1` |
| app 内浮层 | 一张 canvas，正常合成 | **两层**：高亮单独一层带 `mix-blend-mode: multiply` |

## 二、app 内要分两层

只把整层批注 canvas 设成 `mix-blend-mode: multiply` 是**不行的**：

- 删除线压在黑字上 → `0 × 红 = 0` → 线变黑，直接看不见；
- 手写/方框同理，压在任何深色内容上都会"被吃掉"。

所以每页两张 canvas：

| 层 | 内容 | 合成 |
|---|---|---|
| `.annot-layer-under` | 只有 `highlight` | `mix-blend-mode: multiply` |
| `.annot-layer-over`  | 下划线 / 删除线 / 手写 / 方框 / 文本框 | 正常 |

两层都遵守 M7 的老规矩：**没东西可画就不建 canvas**（600 页文档不能每页两张 2× 位图）。
`blendGroupOf(a)` 是唯一的分流判据，写在一处，`draw.ts` 里。

⚠️ `.page-slot` 必须 `isolation: isolate`。否则 under 层的 multiply 会去跟视口深色背景相乘，
页面还没渲染出来时高亮会变成一团黑。

## 三、顺手堵掉的同源坑：高亮色板里的黑与白

色板里本来有黑 `(0.07,0.07,0.09)` 和白。既然高亮走 Multiply：

- **黑**：整行被乘成黑的，字直接消失 —— 比"盖板"还糟；
- **白**：乘以白什么都没做，画了跟没画一样。

高亮工具因此只显示 **8 色**（`HIGHLIGHT_SWATCHES`），其他工具仍是 10 色。
`sanitizeToolColor()` 再兜一层：localStorage 里可能留着旧版本存的黑色高亮色，
不兜的话用户升版本后会莫名其妙画出一行黑条，还不知道怎么恢复。

## 四、验证：判据必须是**浏览器合成后的真实像素**

这次的核心断言不好写，因为"数据对了"和"看起来对"在这一题上完全是两回事。
用了三道关：

1. **同区域像素对比**：高亮前先截下那行文字的图，高亮后再截一次，两张 PNG 丢回页面里
   解码（用浏览器自带解码器，省掉 Node 端 PNG 库）逐像素比：

   | 断言 | 判据 | 为什么有牙 |
   |---|---|---|
   | 🔴 没有字的像素被**提亮** | 所有"原本是字的像素"必须 `lum_后 ≤ lum_前 + 2` | Multiply 只能变暗；盖板写法会提亮 |
   | 字仍是深色 | 字像素平均亮度 `< 45` | 盖板写法约 80 |
   | 白底真被染色 | 白底像素均值 ≈ 高亮色 ±35 | 防止"其实没画上去" |

2. **结构断言**：`.annot-layer-under` 存在、`getComputedStyle().mixBlendMode === 'multiply'`、
   着色像素中不透明占比 >85%（盖板写法是 **0**）。
   ⚠️ 不能要求"100% 不透明"—— 四边形边界的抗锯齿天生半透明。

3. **判据有牙的证明**（项目铁律：测试要真能抓到）。把 `mix-blend-mode` 临时改成 `normal`
   （即当初的"半透明板"行为），测试立刻变红：

   ```
   ❌ 高亮后没有一个字的像素被提亮   被提亮 1266px，字亮度 86.2 → 131.7
   ❌ 字在高亮区里仍然是深色          平均亮度 131.7（改前 86.2）
   ```

   实测数据（改对之后）：`被提亮 0px，字亮度 86.2 → 14.5，底色 rgb(26,184,139)`。

## 五、跨查看器（PDFium）复核

`scripts/make-highlight-variants.mjs` 加了一行 **V4 = `Multiply` 但 `ca=0.55`**，
和 V1（`ca=1`）并排放在同一页，`npm run variants` 生成后在 Edge 里看：

| 行 | 写法 | Edge（PDFium）表现 |
|---|---|---|
| V1 | `/AP` + Multiply, `ca=1` | ✅ 字清晰（**当前实现**） |
| V4 | `/AP` + Multiply, `ca=0.55` | ⚠️ 字发灰、对比度明显下降 ← 根因的直接证据 |
| V2 | `/AP` 普通填充 | ❌ 实心块，字完全不见 |
| V3 | 不给 `/AP` | ✅ 字可见（查看器自画） |

`written.pdf` 在 pdf.js 与 Edge 里各看一遍：Line 4 的文字在黄色高亮上保持纯黑，两边一致。
