# M9 · 触屏可用 + 打包成应用

> 用户原话：**"我在 surface 上的触屏使用体验很糟糕，无法像 edge 的 pdf 编辑器那样进行编辑。
> 主要表现在点击了编辑功能（比如高亮、手写），在浏览器上拖动时会拖动页面返回上一页
> 而不是进行编辑。"**
>
> 结论先写：两个问题都解决了，而且**复现了原 bug 本身**。
> 新增触屏端到端 **22/22**、安装能力 **15/15**，全部回归合计 **197 项全绿**。

---

## 一、根因：三层，缺一层都修不好

触屏代码从 M2 到 M8 **一行都没有**。这不是"体验欠佳"，是根本没处理 ——
所有指针逻辑都是照鼠标写的（`pointerdown` 当作"按下左键"用）。

| # | 机制 | 症状 |
|---|---|---|
| ① | 没设 `touch-action`（默认 `auto`） | 浏览器在 touchstart 后先观察一段，判定为 pan → 自己接管滚动，**并给页面发 `pointercancel`**。编辑器的 `cancelSession()` 一收到就清掉正在画的那一笔 |
| ② | 滚动容器滚到边界后 **overscroll** | Edge/Chrome 把这次 overscroll 翻译成历史导航 → **返回上一页** |
| ③ | 页面可双击缩放 | 触屏上快速两下就缩放，跟画笔抢手势 |

⚠️ **① 和 ② 是两件事，必须分开修**：

- `touch-action` 管的是「**这一片区域的手势归谁**」
- `overscroll-behavior` 管的是「**滚到头之后还能干嘛**」

只加 `touch-action` 拦不住导航；只加 `overscroll-behavior` 则笔画照样被 cancel。

## 二、修复

### 2.1 分层声明 touch-action

| 层 | 值 | 理由 |
|---|---|---|
| `html, body` | `manipulation` | 关掉双击缩放，保留 pan（普通滚动不受影响） |
| `.viewport`（**无工具**） | `pan-x pan-y` | 让浏览器原生滚动 —— 有惯性、有橡皮筋，手写的比不了 |
| `.viewport.tool-drawing`（**绘图工具**） | `none` | **单指归我们**。这是「一拖动笔画就没了」的唯一解 |
| `.viewport`（**标记工具**） | 保持 `pan-x pan-y` | ⚠️ 高亮/下划线/删除线要靠**浏览器原生选区**选中文字，一关就选不中了 |

### 2.2 overscroll 与"手势开始前"

```css
html, body { overscroll-behavior: none; }     /* 总开关 */
.viewport  { overscroll-behavior: contain; }  /* 滚动链不外泄到 document */
```

⚠️ **`touch-action` 只能在手势开始前生效**。等第二根手指落下再改已经晚了 ——
浏览器在 `touchstart` 那一刻就决定了这次手势归谁。所以「工具激活 → 切换 touch-action」
是唯一可行的时机，也正因如此**工具激活期间单指翻不了页**（见下）。

### 2.3 双指手势：单指被占用后的唯一出路

tool-action 一关，手指就翻不动页了。所以补一套双指手势（对齐 Edge 绘图模式）：

| 手势 | 行为 |
|---|---|
| 双指拖动 | 平移视口 |
| 双指捏合 | 缩放（以手指中心为锚点） |

实现要点（`src/viewer/PdfViewer.vue`）：

- 只对 `pointerType === 'touch'` 记账。鼠标/触控笔不走这里 ——
  对它们来说"多指"没有意义，混进来会让一次普通拖拽被判成手势。
- **平移与缩放共用一个锚点公式**：让「手势开始时手指按住的那个内容点」始终跟着手指中心走。
  分别处理必然打架（捏合时画面往一边漂）。推导见代码注释，
  关键结论是 `content` 的布局位置 `L` 会被消掉，所以公式里只用 `getBoundingClientRect()`，
  不需要知道它到底在哪 —— 也就不需要 `nextTick`（滚轮缩放那条路径用了 `nextTick`，
  是因为它没做这个消元）。
- 第二根手指落下时**必须 `cancelSession()`** —— 第一指已经开了一次绘制会话，
  不清掉的话手指一抬就提交一条乱线。
- 参与手势的两个 `pointerId` 要**固定住**：中途抬指后再按下的新手指会让"前两个"换人，
  中心点和指间距会跳变。
- 落定提交按**手指中心**锚定（`scheduleCommit({x,y})`）。用视口中心会让画面明显跳一下。

## 三、打包成应用

### 3.1 PWA（已就绪）

| 件 | 作用 |
|---|---|
| `public/manifest.webmanifest` | `display: standalone` → 独立窗口，无地址栏无标签栏 |
| `public/icons/*.png` | 192 / 512 / maskable 512。由 `npm run icons` 用 zlib 手写 PNG 生成（零依赖，改配色改常量即可） |
| `public/sw.js` | Service Worker：app shell 预缓存 + 运行时缓存，离线可用 |
| `index.html` | `viewport-fit=cover`、`maximum-scale=1`、manifest 链接、theme-color |

**SW 的两条策略红线**：

1. **绝不缓存 PDF**。教材几十 MB，会撑爆配额（Chrome 每源约 60% 可用磁盘）还拖慢首开。
   `Range` 请求也不碰（会破坏 206 语义）。
2. 导航请求走 **network-first**（发布新版刷新就拿到），静态资源走
   stale-while-revalidate（带 hash 的 URL 变了本来就不会命中旧条目）。

⚠️ SW **只在生产构建注册**。dev 模式下模块是即时编译的，SW 会把旧模块缓存下来，
改一行要手动清缓存才生效。

### 3.2 一键启动（`npm run app` / `start-app.bat`）

起静态服务 + 自动打开浏览器 + 提示安装。

### 3.3 🔴 最关键的现实约束：**局域网 IP 装不了**

`http://192.168.x.x` **不是安全上下文** → Service Worker 注册直接失败 →
「安装为应用」永远不会出现，而且**不给任何提示**。

所以在 Surface 上想装成应用，只有两条路：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 在 Surface 本机跑**（推荐） | 把仓库拷过去 → `npm i && npm run build` → 双击 `start-app.bat` → 点「安装为应用」 | 需要在 Surface 上装 Node |
| B. 局域网打开 | 直接用 `npm run serve:dist`，功能全都能用，只是**装不了应用** | 触屏修复照样生效，只是没有独立窗口 |

⚠️ 换句话说：**触屏修复和"装成应用"是两件独立的事**。
前者在任何打开方式下都生效；后者要求 localhost（或 HTTPS）。

## 四、验证

### 4.1 判据设计：先证明"浏览器有没有把手势抢走"

光断言 CSS 值不够 —— 得看**真实事件序列**。探针挂在 `.viewport` 上统计 pointer 事件：

> **浏览器一旦决定自己滚，就会给页面发 `pointercancel`。**

于是有了干净的双向对照：

| 场景 | down | move | cancel | 结论 |
|---|---|---|---|---|
| **无工具**单指滑动 | 1 | 1 | **1** | 浏览器接管滚动 —— 这是**正常且期望**的 |
| **有工具**单指拖动 | 1 | **12** | **0** | 手势完全归我们，一笔都没被抢 |

这不是"看起来能用"，是**机制层面对上了**。

### 4.2 判据有牙（铁律）：复现原 bug 本身

把 `.viewport.tool-drawing { touch-action: none }` 临时改回 `pan-x pan-y`，重跑：

```
[3] 核心：激活手写后单指拖动 = 画（不能被抢）
  ❌ 手写工具激活 → touch-action 变成 none        touch-action=pan-x pan-y
  ❌ 拖完页面还在（没被「滑动返回上一页」带走）   ⚠️ 页面已被导航走 — 这正是用户报的那个 bug 复现了
```

⚠️ **第二行是意外收获**：旧行为下横向拖拽真的把页面导航走了，
`.viewport` 连同页面一起消失，后续断言直接崩在 `null.scrollTop`。
这个崩溃本身**就是用户描述的现象**，所以把它提升成了一条正式断言
（并配了 `99-navigated-away.png` 截图）。以后再退化，测试会明确说"页面被导航走了"，
而不是给一堆 `Cannot read properties of null` 的假错误。

### 4.4 两个测量陷阱（踩了）

1. **`Page.getAppManifest` 的 `parsed` 不是清单内容**。
   实测它只有 `{scope}`，真正的清单在 `data` 里（原始 JSON 文本）。
   用错字段的症状是 `name/display/icons 全是 undefined`，看着像清单写错了。
2. **`Input.dispatchTouchEvent` 必须逐帧间隔**。一口气把 12 帧全发出去，
   浏览器来不及"观察位移"，可能一个 `pointermove` 都不派发。

## 五、已知限制（要写进 UI / 交代用户）

| 限制 | 说明 |
|---|---|
| **工具激活时单指不能翻页** | 被绘图占用了，改双指。已用 toast 提示一次（触屏设备上首次进工具时） |
| **触屏上高亮选字手感未知** | 走的是浏览器原生长按选区，没有专门优化。扫描版书本来也没有文本层 |
| **局域网 IP 装不了应用** | 安全上下文硬约束，见 §3.3 |
| **没做 Tauri / Electron** | `npm run app` + PWA 已能满足"独立窗口的应用"。真 exe 需要 Rust 工具链，且要在 8GB 机器上编译 |
| **双指手势没有惯性** | 松手即停。原生滚动有惯性，但我们只在工具激活时才接管 —— 那时本来也不是在滚动 |
