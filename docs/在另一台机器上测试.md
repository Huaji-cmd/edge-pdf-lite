# 在另一台机器上测试 & `toHex` 报错的来龙去脉

日期：2026-10-11

---

## 一、`a.toHex is not a function` 是什么

**不是我们的代码有问题，是 pdf.js 的兼容性地雷。**

pdfjs-dist 6.x 的默认构建**直接调用 ES2025 的新 API，且不做任何降级**。
浏览器缺这些 API 时，**worker 线程直接死掉** —— 表现是"整个 PDF 打不开"，
而不是某个页面渲染失败。错误信息就是 `a.toHex is not a function`（`a` 是压缩后的变量名）。

实测确认 pdf.js 6.4.299 用到了这些：

| API | 需要的最低浏览器版本 |
|---|---|
| `Uint8Array.prototype.toHex` | Chrome / Edge **140** |
| `Uint8Array.prototype.toBase64` | Chrome / Edge **140** |
| `Uint8Array.fromBase64` | Chrome / Edge **140** |
| `Uint8Array.prototype.setFromBase64` | Chrome / Edge **140** |
| `Math.sumPrecise` | Chrome / Edge **137** |
| `Promise.try` | Chrome / Edge **128** |
| `Promise.withResolvers` | Chrome / Edge **119** |

> 开发机上的 Edge 够新，所以本地跑得好好的；你一换机器就炸 —— 这就是原因。
> 对一个"面向不常更新的低配 Windows"的项目来说，这个坑必须堵死。

### 怎么修的

**没有换 legacy 构建**（那是转译 + core-js 降级版，会牺牲渲染性能），
而是走「现代构建 + 自带 Polyfill」：

```
src/pdfjs/polyfills.ts     # 只在 API 缺失时才打补丁；浏览器够新时零开销
src/pdfjs/pdfWorker.ts     # 自定义 worker 入口：先补丁，再加载 pdf.js 的 worker
src/pdfjs/index.ts         # 统一装载入口，业务代码一律从这里 import
```

**关键点：主线程和 worker 两个线程都要补。** 只补一边 = 一边能过、另一边炸。
`src/pdfjs/index.ts` 同时负责这两件事，所以业务代码只要：

```ts
import { pdfjsLib, installPdfWorker, AnnotationMode } from '@/pdfjs'
installPdfWorker()          // 用 getDocument 之前调用一次
```

绝不要直接 `import * as pdfjsLib from 'pdfjs-dist'` —— 那会绕过补丁和 worker 装配。

### 验证方式（已通过）

用 CDP 在页面加载前删掉那 8 个 API，精确模拟旧浏览器：

```bash
EPL_OLD_BROWSER=1 node scripts/spike-run-crop-render.mjs
```

结果：8 个 API 全部识别为缺失并补齐，
**2.2MB 的真实论文照常打开**；现代浏览器下则一个都不用补。

## 二、先搞清楚：哪台机器跑什么

**这是最容易搞错的一步。** 两台机器的分工是：

| | 开发机（项目所在的机器） | 目标机（那台 8GB 低配机） |
|---|---|---|
| 需要装 Node / 项目源码吗 | 需要 | **完全不需要** |
| 要跑什么命令 | `npm run build` + `npm run serve:dist -- --lan` | **什么都不用跑** |
| 干什么 | 构建 + 当服务器 | **只用浏览器打开一个网址** |

**目标机上不需要、也不应该跑 npm。** 那边的浏览器负责渲染和性能表现，
服务跑在开发机上 —— 这正是我们要测的东西：**目标机的浏览器 + 目标机的 GPU**。

### ⚠️ 一个很常见的误操作

在目标机上敲 `npm run build`，会得到：

```
npm error code ENOENT
npm error path C:\Users\xxx\package.json
npm error Could not read package.json: no such file or directory
```

**原因**：`npm run` 会在**当前目录**找 `package.json`。
目标机上既没有这个项目，命令行还停在用户主目录里（`C:\Users\你的用户名>`），当然找不到。

这不是环境坏了，是**命令敲错机器了**。正确的做法见下面。

## 三、实际操作

### 路线 A（推荐）：构建产物 + 静态服务器

**在开发机上**：

```bash
cd <项目目录>
npm run build
npm run serve:dist -- --lan
```

⚠️ **`--lan` 不能省**。`npm run serve:dist` 现在**默认只监听本机回环**（以前默认是全开，
等于每次跑都把这个端口和 dist 目录暴露给同网段的所有人）。不带 `--lan` 时另一台机器
打不开，而且现象是"连不上"，很容易被误判成防火墙问题 —— 脚本会打印一行提示告诉你这一点。

脚本会自己算出该用哪个网卡地址，然后打印类似：

```
  ⚠️ --lan：已经对同网段开放。别在公共 WiFi / 校园网上这样跑。

  ▼ 在【另一台机器】上，只用浏览器打开下面这个地址：

      http://192.168.x.x:4173/spike.html      ← 用这个
```

**在目标机上**：把这个网址敲进浏览器，回车。完事。

### 路线 B（边改边测）：开发服务器开在局域网

```bash
npm run dev:host
```

注意必须带 `--host`。**默认的 `npm run dev` 只监听 `[::1]`（本机回环），
局域网里的另一台机器是连不上的** —— 这一点很容易被误判成"防火墙问题"。

命令行里会打印 Network 那一行，用那个地址。
**但做性能对比请用路线 A** —— 开发服务器带 HMR、代码未压缩，数字不可比。

### 防火墙

任何一条路线，**首次都会弹 Windows 防火墙提示，必须选「允许」**。
如果当时点了"取消"或者根本没弹，手动补一条规则（在开发机上，管理员 PowerShell）：

```powershell
New-NetFirewallRule -DisplayName "edge-pdf-lite" -Direction Inbound `
  -Protocol TCP -LocalPort 4173,5173 -Action Allow
```

### 路线 C（最终形态）：Tauri 打包成 exe

M8 才做。那才是你要的日常使用方式。

## 四、连不上 / 报错时怎么排查

按顺序做，一步就能定位：

1. **先在开发机上用 `http://localhost:4173/spike.html` 自测。**
   本机都打不开 → 是服务没起来；本机能打开 → 问题在网络，继续往下。
2. **确认两台机器在同一局域网。** 手机热点也行，但公司/学校网络可能做了客户端隔离。
3. **确认用的是正确的 IP。** 开发机上跑 `ipconfig`，找有默认网关的那个适配器。
   本项目脚本已自动识别默认出口网卡，认准输出里带「用这个」字样的那一行。
4. **防火墙**：见上面。

### ⚠️ 服务必须一直活着

这是最容易踩的一脚：**页面能打开 ≠ 后面就一直能用。**

`spike.html` 打开后，pdf.js 的 worker 脚本是**点「跑实验」那一刻才去下载的**。
如果这期间服务停了，就会看到：

```
出错：Setting up fake worker failed:
"Failed to fetch dynamically imported module: http://192.168.x.x:4173/assets/pdfWorker-xxxx.js"
```

**注意措辞**：`Failed to fetch` 是**网络层失败**（连接被拒 / 中断），不是"文件不存在"。
**跑 `npm run serve:dist -- --lan` 的那个终端窗口别关**，关掉窗口 / Ctrl+C 都会导致这个报错。

### 另一种相似的报错，原因完全不同

```
Failed to load module script: Expected a JavaScript module script
but the server responded with a MIME type of "text/html"
```

这才是**文件不存在**（页面引用的构建产物和 dist/ 里的对不上，通常是改了代码没重新 build）。
`scripts/serve-dist.mjs` 早期版本会把找不到的资源回落到 `index.html`，把 404 伪装成 MIME 问题 ——
已修复，现在缺失资源老实返回 404。遇到这种就 `npm run build` 重新构建再刷新。

## 五、目标机的实测画像（2026-10-11，来自截图）

| 项 | 值 | 含义 |
|---|---|---|
| 浏览器 | Chrome / Edge **154** | 高于 140，不触发 `toHex` 那个坑；Polyfill 显示"无" |
| **WebGL 渲染器** | **ANGLE (Intel, Intel(R) Iris(R) Plus Graphics, D3D11)** | ✅ **有硬件 GPU 加速**。那条"软件光栅化慢 6.5 倍"的最坏情况**不成立** |
| 设备像素比 | **2** | ⚠️ 要紧，见下 |
| 逻辑核心数 | 8 | 不算差 |
| 设备内存 | 未知 | `navigator.deviceMemory` 需要安全上下文，HTTP + 局域网 IP 下取不到；不影响使用 |
| 是否安全上下文 | false | 局域网 IP + HTTP 的必然结果。**打包成 Tauri 后是 `tauri://localhost`，属于安全上下文，这个限制会消失** |

### dpr = 2 是个要紧的事

在 dpr=2 的屏上，一页 PDF 的 canvas 像素数是 dpr=1 时的 **4 倍**。按 A4 页算：

| scale | dpr=1 画布 | dpr=2 画布 |
|---|---|---|
| 1.0 | 0.5 MP | 2.0 MP |
| 2.0 | 2.0 MP | **8.0 MP** |
| 2.7 | 3.6 MP | **16.0 MP** ← 撞上 pdf.js 上限，开始发虚 |
| 4.0 | 8.0 MP | 32.0 MP（约 128 MB） |

**在这台机器上大约 scale 2.7 就撞到 16MP 上限**，比 dpr=1 的机器（约 scale 5.4）早一半。
所以裁剪渲染的价值在这台机器上**比在开发机上测出来的更早体现**。

## 六、目标机的操作清单

打开 `spike.html`，**页面顶部有一块「环境信息」**，不用点任何按钮就会显示：

| 字段 | 要看什么 |
|---|---|
| 浏览器 | 低于 Edge 140 → 会踩 `toHex`（已修，但要知道） |
| 已补齐 Polyfill | 列出东西 = 这台机器浏览器偏旧、补丁真的生效了；"无" = 版本够新 |
| **WebGL 渲染器** | **最关键**：显示 SwiftShader / llvmpipe / "无" = 没有 GPU 加速 |
| 设备像素比 | dpr=2 会让 canvas 像素数翻 4 倍，直接决定缩放上限策略 |

然后**换几个你平时觉得卡的 PDF** 跑实验，把「整页耗时 / 裁剪耗时 / 提速」三列发我。

## 七、如果以后要脱离开发机

`public/` 下的 `cmaps`、`standard_fonts`、`testdata` 都是脚本生成的（已在 `.gitignore`）。
`npm run build` 会把它们一起拷进 `dist/`，所以：

- **只拷 `dist/` 就够了**，目标机不用装 Node、不用源码。
- 但**不能直接双击 `dist/spike.html`** —— ES 模块和 Worker 在 `file://` 下会被浏览器拦掉。
  必须用 HTTP 提供。最省事还是服务跑在开发机上，目标机只用浏览器访问。
- 最终形态是 M8 的 Tauri exe，那时双击即用，不再有这些约束。
